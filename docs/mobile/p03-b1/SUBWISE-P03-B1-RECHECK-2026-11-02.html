F3（high）两个校验脚本恒 exit 0，证据缺失无显式信号 —— 已修

现象：脚本崩溃时 ios-run.json / harmony-build.json 整个不存在。 上传步骤用 if-no-files-found: warn 不会报错；continue-on-error: true 进一步掩盖退出码。 结果是「文件不存在」与「文件里写着 NOT_RUN」在 CI 上表现完全一样 —— 无法区分 「环境不具备，本次没做」和「脚本自己崩了，证据没产出」。这是最危险的一种状态： 容易把一次静默失败读成一次诚实记录的未执行。

根因：verify-ios-simulator.sh 有 8 处 exit 0、 build-harmony-linux.sh 有 6 处 exit 0。失败结果只存在于 JSON 内容里， 而 JSON 可能压根不存在。

已实施的修法：

  1. 两个脚本各加 EXIT 兜底（on_exit + trap on_exit EXIT）： FINAL_RECORDED / EVIDENCE_WRITTEN 标记区分「已写过结论」与「异常中止」； 任何非正常结束补写 status=ERROR，error 明写「这是脚本自身失败，不等于环境不具备」。 trap 装在静态核验之前（那一步自己也会崩）。iOS 脚本原有的独立 EXIT trap（模拟器 shutdown） 并入 on_exit，保证每个脚本只有一个 EXIT trap —— 多个 trap 会互相覆盖，兜底就失效。
  2. 新增 mobile/p03-b/scripts/check-evidence-status.py：读证据 JSON 的 status 与期望值比对，不符则 ::error:: 标红并贴出原因。 文件缺失、JSON 非法、缺 status 字段一律 exit 1。
  3. 两个 workflow 各加一步判定：iOS job 判 RUN，HarmonyOS job 判 COMPILE_OK。判定步骤排在所有上传之后，避免判红时把产物和证据丢掉。

实施中发现的第二个漏洞：if: always() 缺失

第一次实现只加了判定步骤，验收时用崩溃注入发现：判定步骤自己也会被跳过。 GitHub Actions 默认「上一步失败 → 后续步骤跳过」，于是鸿蒙编译步骤崩溃（exit≠0）→ 「上传 HAP」和「判定编译结果」全被跳过 → 产物和刚写出来的 ERROR 证据一起丢失， 等于绕了一圈回到原来的问题。

修法：鸿蒙 4 个步骤与 iOS 3 个步骤全部加 if: always()； 两个 workflow 的 if-no-files-found: error 改为 warn； 鸿蒙编译 run 改为 bash ... || echo ::error::；概要步骤读 JSON 改为容错。

验收：用 YAML 解析断言每个步骤的 if / continue-on-error / if-no-files-found，并断言判定步骤排在所有上传之后 —— 12 项断言全绿。

残留边界：SIGKILL / OOM kill 这类硬终止不会被 shell trap 捕获。 这种情况仍需靠 CI 侧判定步骤发现「证据缺失」来兜 —— 但那一次会明确报「证据文件不存在」， 而不是静默。

验收：崩溃注入（未定义变量触发 set -u 中止）→ 两个脚本均产出 status=ERROR 且与 NOT_RUN 可区分；正常路径不受影响（Linux 上 iOS 仍 NOT_RUN， 鸿蒙真实编译仍 COMPILE_OK / 50,768 字节 / ERROR 0 / WARN 2）；判定脚本 6 种输入全部符合预期； 端到端为「脚本 exit 0 + 判定 exit 1」，符合设计。

七、三端设备验证路径

FA 提供了三台可用设备：Android 虚拟机、Mac mini M4、荣耀鸿蒙真机。 服务器是无 KVM 的 Linux（4 核 3.6GB），模拟器会被 OOM killer 杀掉， 不适合长期占用生产机 —— 因此改为交付设备端脚本，由 FA 在自己设备上跑， 产出机器可读证据回来，由本轮统一复核归档。

服务器侧短暂尝试的真实结果

  • API 30 模拟器 boot 约 400 秒；sys.boot_completed 始终未置位， 但 shell 与 logcat 都可用 —— 判据应是「shell 能响应」，不是等 boot 属性。
  • 首次启动弹出 "System UI isn't responding" ANR 弹窗盖住界面， 导致 uiautomator dump 只返回系统层级，误判成「应用没渲染」。 关掉弹窗后拿到完整 UI 层级，Subwise 界面渲染完全正常 （"SQLite 已打开 · 已读取本地记录"、"本地暂无快照"、"写入模拟数据并从 SQLite 读取" 都在）。
  • 第二次启动 qemu 被 OOM killer 杀掉（可用内存仅 615MB，swap 1.6G/1.9G 打满）。 → 结论：服务器不是跑模拟器的合适环境。
