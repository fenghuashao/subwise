## 六、遗留缺陷（待下一轮处理）

### F3（high）两个校验脚本恒 exit 0，证据缺失无显式信号 —— **已修**

**现象**：脚本崩溃时 `ios-run.json` / `harmony-build.json` 整个不存在。上传步骤用的是
`if-no-files-found: warn`，不会报错；`continue-on-error: true` 进一步掩盖退出码。
结果是「文件不存在」与「文件里写着 NOT_RUN」在 CI 上表现完全一样 —— 无法区分
「环境不具备，本次没做」和「脚本自己崩了，证据没产出」。这是最危险的一种状态：
容易把一次静默失败读成一次诚实记录的未执行。

**根因**：`verify-ios-simulator.sh` 有 8 处 `exit 0`、`build-harmony-linux.sh` 有 6 处 `exit 0`。
失败结果只存在于 JSON 内容里，而 JSON 可能压根不存在。

**已实施的修法**：

1. **两个脚本各加 EXIT 兜底**（`on_exit` 函数 + `trap on_exit EXIT`）：
   - `verify-ios-simulator.sh` 用 `FINAL_RECORDED` 标记，`build-harmony-linux.sh` 用
     `EVIDENCE_WRITTEN` 标记，区分「已由 `record()` / `write_evidence()` 写过结论」
     与「异常中止」。
   - 任何非正常结束都补写一份 `status=ERROR` 的 JSON，`error` 字段明写
     「这是脚本自身失败，不等于环境不具备」。
   - trap 装在**静态核验之前**（那一步自己也会崩），不是只覆盖动态段。
   - iOS 脚本原本那条独立的 `trap ... EXIT`（模拟器 shutdown）**并入** `on_exit`，
     保证每个脚本只有一个 EXIT trap —— 多个 trap 会互相覆盖，兜底就失效了。
2. **新增 `mobile/p03-b/scripts/check-evidence-status.py`**：读证据 JSON 的 `status`
   并与期望值比对，不符则 `::error::` 标红并贴出原因。文件缺失、JSON 非法、
   缺 `status` 字段一律 exit 1。
3. **两个 workflow 各加一步判定**：`build-mobile.yml` 的 ios job 判 `RUN`，
   `build-harmony.yml` 判 `COMPILE_OK`。判定步骤**排在所有上传之后**，
   避免判红时把产物和证据丢掉。

### F3 实施中发现的第二个漏洞：`if: always()` 缺失

第一次实现只加了判定步骤，验收时用崩溃注入发现：**判定步骤自己也会被跳过**。

GitHub Actions 的默认行为是「上一步失败 → 后续步骤跳过」。于是：

- 鸿蒙「编译并产出证据」步骤崩溃（exit≠0）→ 该步骤标记失败 →
  「上传 HAP」和「判定编译结果」**全被跳过** → 产物和刚写出来的 ERROR 证据一起丢失。
  这等于绕了一圈回到原来的问题：失败时看不到任何材料。
- iOS 侧靠 `continue-on-error: true` 兜住了编译步骤，但「上传 app」步骤失败时
  仍会跳过判定；而 `if-no-files-found: error` 会让上传失败直接终止整个 job。

**修法**：

- 鸿蒙「编译并产出证据」「上传 HAP 与证据」「判定编译结果」「概要」全部加 `if: always()`；
  编译步骤的 run 改为 `bash scripts/build-harmony-linux.sh || echo "::error::..."`，
  让脚本的 exit≠0 不再阻断流程，同时把错误显式打到日志里。
- iOS 的两个上传步骤与判定步骤全部加 `if: always()`。
- 两个 workflow 里的 `if-no-files-found: error` 全部改为 `warn` ——
  上传失败不该终止 job，判定步骤才是决定成败的地方。
